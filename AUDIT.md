## 4. Что уже сделано правильно

- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`,
  `webSecurity: true` — `src/main/main.js:535`.
- Ограничивающая CSP; нет inline JavaScript/eval-разрешения, запрещены
  connect/object/frame/form — `src/renderer/index.html:5`.
- IPC завернут в проверку конкретного `webContents` и URL —
  `src/main/main.js:503`. Preload не отдаёт renderer объект IPC-события.
- Ограничены навигация и новые окна; внешние ссылки допускают только HTTP(S).
- SSH host key проверяется; первый/изменившийся ключ требует решения
  пользователя, безопасная кнопка выбрана по умолчанию — `main.js:662`.
- Обычные сохранённые `password`/`passphrase` скрыты из представления
  подключения для renderer и шифруются через `safeStorage`.
- Конфиг сохраняется через временный файл и rename; есть ограничение размера,
  карантин повреждённого JSON и восстановление из резервной копии.
- Проверяются SFTP entry names, часть опасных путей, глубина рекурсии,
  локальные symlink; скачивание каталога не сливается с существующей папкой.
- Туннели слушают `127.0.0.1`, а не все интерфейсы.
- GitHub Actions закреплены полными SHA; npm audit включает devDependencies,
  где находится поставляемый Electron; в release задан `--publish never`.
- В коде crashReporter отключена автоматическая отправка; явных SDK
  телеметрии в просмотренных исходниках не обнаружено.

Эти меры согласуются с [рекомендациями Electron по безопасности](https://www.electronjs.org/docs/latest/tutorial/security).
Их надо сохранить при исправлениях. Наличие настроек fuses в package.json
не заменяет проверку фактических fuses собранного Windows executable.

## 6. Карточки проблем

### A01 — ввод после SSH reconnect идёт в старый ID

**Места:** `src/renderer/renderer.js:145`, `:184`, `:237`, `:249`, `:1274`, `:1296`.

`makeTerm(sessId, ...)` захватывает неизменяемый аргумент `sessId` в callback
`term.onData`, обработчике wheel и обработчике фокуса. `reconnectTab` меняет
`tab.id`, `tabs`, `paneOf`, dataset, но сохраняет прежний объект xterm и callbacks.
Вкладка пишет «соединение восстановлено», вывод может приходить, однако ввод
отправляется в удалённый из `sessions` ID. Возврат фокуса также возвращает
`focusedSessId` к старому значению. В broadcast поведение может выглядеть иначе,
поскольку актуальные ID добавляются отдельным проходом.

**Воспроизведение:** `node audit/reproduce.cjs`, A01: после смены `old → new`
вызов callback ввода по-прежнему отправляет `old`.

**Исправление:** отделить стабильный ID панели от меняющегося ID соединения.
Все пути ввода должны брать актуальную сессию через одну привязку панели;
или пересоздать подписки с обязательным disposal старых. Проверить также wheel,
paste, focus, resize, split, монитор и туннели.

**Приёмка:** после одного и нескольких обрывов ручной ввод, вставка и wheel
попадают только в новую сессию; обычный `exit` не должен трактоваться как
неожиданный обрыв без явно выбранной политики пользователя.

### A02 — секреты профиля не привязаны к его endpoint и auth mode

**Места:** `src/main/main.js:410–426`, `:708–716`;
`src/renderer/renderer.js:522–538`, `:571–574`.

`resolveSshConfig` независимо выбирает `host`, `port`, `username`, `keyPath`
из входных полей, а пароль берёт как `source.password || decSecret(saved.password)`.
Одинаковый `id` позволяет изменить адрес/пользователя и автоматически использовать
секрет старого профиля. Пустая строка не означает «не использовать пароль».
При переключении key → password renderer вообще не передаёт `keyPath: ''`,
поэтому main подставляет сохранённый ключ. Обратное переключение тоже может
оставлять прежний пароль дополнительным способом входа.

**Условия и влияние:** редактирование профиля, подключение к другому адресу
без повторного ввода секрета. Host-key verification остаётся включённой:
неизвестный сервер надо сначала подтвердить; ранее доверенный адрес может
подключиться сразу. Поэтому это не доказанный обход проверки SSH/MITM, но
ошибка выбора получателя секрета и методов аутентификации.

**Воспроизведение:** A02 использует синтетический профиль и показывает,
что старый пароль и keyPath остаются при изменённых host/username.

**Исправление:** явный контракт `profileId + overrides + authMode`,
различать отсутствие поля и явную очистку. Повторное использование секрета
при смене endpoint/username должно требовать явного решения. Хранить в
вкладке фактически использованные параметры: `stored || cfg` сейчас может
подставить старый профиль для будущего split/reconnect.

**Приёмка:** матрица old/new endpoint, password/key, сохранён/не сохранён,
пустой пароль, ошибочный пароль, изменённый профиль без сохранения.

### A03 — нормализация JSON не проверяет схему настроек

**Места:** `src/main/utils.js:28–37`; `src/main/main.js:323–344`, `:1356–1362`;
`src/renderer/renderer.js:867–886`, `:890–905`, `:2311–2314`, `:2612`.

`normalizeConfig` чистит prototype keys и ограничивает глубину, но оставляет
типы значений и структуру settings практически произвольными. Файл
`{"format":"meowshell-config","version":1,"settings":{"snippets":{}}}`
успешно импортируется, а `renderSnippets` падает на `.forEach`.
`customThemes: {x: null}` аналогично ломает `mergeCustomThemes`.
Неправильные fontSize, scrollback, cursorStyle и theme могут приводить к
исключениям и некорректному состоянию xterm.

**Влияние:** после импорта возникает постоянная неисправность UI; файл остаётся
валидным JSON, поэтому механизм восстановления повреждённого JSON не срабатывает.
Предел записанного конфига также не согласован с пределом чтения: saveConfig
может успешно сохранить документ больше 10 МБ, который следующий loadConfig
объявит повреждённым.

**Исправление:** одна версия схемы для загрузки, импорта, изменения и экспорта;
allowlist настроек, типы, enum, числовые и суммарные byte limits, валидация
элементов snippets/tunnels/themes/connections, миграции. Проверять итоговый
размер до записи. Невалидное поле безопасно отклонять или возвращать к default
с понятным сообщением, сохраняя остальные данные.

**Приёмка:** A03 плюс malformed settings, null theme, недопустимые enum,
превышение общего размера; перезапуск после каждого случая.

### A04 — известные уязвимости зависимостей, достижимый YAML DoS

### A05 — каталог для SSH paste-media может остаться публичным

**Места:** `src/main/main.js:1036–1051`.

Результаты `sftp.mkdir(cache, {mode:0700})` и `sftp.chmod(cache,0700)`
игнорируются. Загрузка продолжается даже при отказе установки прав.
Не проверяется, что существующий `~/.meowshell` — каталог текущего пользователя,
а не symlink. Файл записывается обычным `fastPut` без явных приватных прав
и эксклюзивного создания. Случайное имя защищает от простого угадывания,
но не от чтения в доступном другим пользователям каталоге.

**Условия:** существующий небезопасный каталог, ограниченная реализация SFTP,
ошибка chmod/владельца, либо подмена каталога на сервере. На обычном сервере
с рабочим chmod(0700) внешний доступ закрывается — дефект именно в fail-open.

**Воспроизведение:** A05 возвращает EEXIST и permission denied из mkdir/chmod,
но обработчик всё равно вызывает fastPut и отвечает `handled:true`.

**Исправление:** разрешать из mkdir только ожидаемый EEXIST, проверять lstat,
тип/ссылку и реально установленные права, отклонять загрузку при ошибке.
Создавать файл с 0600 и эксклюзивным флагом; предусмотреть приватный временный
каталог и корректную очистку незавершённого upload. Изменения на реальных
серверах делать только в согласованной тестовой директории.

**Приёмка:** chmod denied, symlink, world-readable существующий каталог,
ошибка в середине передачи; приватное содержимое не передаётся при сбое защиты.

### A06 — SFTP upload и редактор записывают поверх исходного файла

**Места:** `src/main/main.js:844–850`, `:919–927`, `:972–983`, `:1456–1463`;
`src/renderer/renderer.js:1451–1477`.

Upload вызывает `fastPut` прямо в конечное имя, редактор — `sftp.writeFile`
прямо в исходный файл. В установленном `ssh2/lib/protocol/SFTP.js:639`
writeFile по умолчанию использует `flag:'w'`; fastXfer также вызывает
`dst.open(dstPath,'w', ...)`. Исходный файл обрезается до успешного завершения
операции. При обрыве сети остаётся пустой/частичный файл. Для upload нет
предварительного подтверждения перезаписи существующего имени. Одиночный
download также пишет прямо в выбранный файл и может испортить уже существующую
локальную копию после подтверждения overwrite в системном диалоге.

**Это установленное поведение пути записи, а не результат destructive E2E:**
настоящие файлы сервера при аудите не перезаписывались.

**Исправление:** upload/edit через уникальный временный файл в том же каталоге,
проверку завершения и commit rename с учётом возможностей SFTP/OpenSSH.
Сохранять права/владельца где это поддержано; различать создание и замену;
подтверждать коллизию имён. Для редактора проверять изменение исходника
другим процессом по mtime/size или более строгому токену версии.
Download — временный локальный файл и замена только после успеха.

**Приёмка:** fault injection на open/write/close/rename и разрыв сети;
до успешного commit исходный файл побайтно неизменен, временный файл
удалён либо явно предложен для восстановления.

### A07 — незавершённые SSH connect и некорректная причина завершения

**Места:** `src/main/main.js:687–760`; `src/renderer/renderer.js:540–546`, `:475–492`.

Promise подключения завершается через ready/shell callback или error,
но у `client` нет обработчика end/close для незавершённого подключения.
Раннее закрытие без error оставляет invoke ожидающим; после успешной
аутентификации нет собственного дедлайна получения shell channel.
Незавершённые клиенты ещё не зарегистрированы в `sessions`, поэтому закрытие
UI не может отменить их по возвращённому ID. На стороне UI await не обёрнут
в finally: reject IPC оставляет кнопку «Подключение…» disabled.

A07 использует настоящий ssh2 Client и локальный TCP endpoint, который
отдаёт синтетический SSH banner и закрывается. Получены end/close без
error/ready; promise обработчика остаётся pending. Проверка проводится
без аутентификации и доступа к реальному SSH-серверу. До получения banner
ssh2 может выдать error — этот отдельный путь не следует путать с находкой.

Дополнительно stream close всегда отправляет `{code:0}`; реальный exit status
и причина обрыва теряются. Renderer автоматически reconnect-ится даже после
обычного пользовательского `exit`, пока включён autoReconnect.

**Исправление:** единая машина состояний подключения с complete-once,
таймаутами всех стадий, end/close/error cleanup, отменой pending connections,
сохранением exit code/signal и явной причиной завершения. UI — try/finally.

**Приёмка:** EOF до banner/ready, аутентификация успешна, shell не отвечает,
отказ host key, отмена диалога, закрытие окна во время connect, штатный exit.

### A08 — живая split-сессия теряет свою панель

**Места:** `src/renderer/renderer.js:349–391`, `:395–428`, `:475–492`, `:1321`.

После естественного выхода основного local shell обработчик вызывает
`closeTab(id,false)`. Эта функция передаёт тот же `false` в `closeSplit`,
который удаляет DOM и mapping, но не посылает kill второй, ещё живой сессии.
То же возможно при неудачном reconnect основного SSH. Процесс/соединение
остаётся в main, продолжает работу без видимой вкладки и может держать ресурсы.
A08 проверяет удаление обеих панелей при отсутствии kill для split.

Также в `splitTab` нет флага pending и проверки `tab.closing` после await:
двойной клик или закрытие вкладки во время connect может создать лишние
сессии и терминалы в отсоединённом DOM. Этот вариант проверен по коду.

**Исправление:** при закрытии панели завершать все принадлежащие ей живые
сессии независимо от причины выхода одной из них, либо явно продвигать split
в основную вкладку. Сериализовать создание split и отменять результат,
если владелец уже закрыт. Таймер закрытия split должен проверять исходный ID,
чтобы не закрыть новую панель после смены состояния.

**Приёмка:** локальный `exit` при живом split, исчерпание reconnect,
двойной split, закрытие во время connect; в main нет потерянных сессий.

### A09 — ограничения metadata не ограничивают память и время

**Места:** `src/main/main.js:823–838`, `:858–881`, `:1443–1450`,
`:1587–1639`, `:1675–1681`.

Редактор ограничивает только `stat.size`, затем делает безлимитный readFile.
Размер может измениться между запросами; сервер может вернуть разные stat/fstat.
Ни потокового счётчика принятых байтов, ни таймаута в приложении нет. A09
синтетически возвращает размер 1 и буфер 2 МБ + 1: приложение принимает его.

readdir сначала собирается полностью библиотекой, и лишь потом применяется
`slice(0,10000)` или счётчик рекурсии. Они ограничивают выдачу/обход, но не
объём уже принятого listing. Монитор копит `out += data` без лимита и timeout;
stopMonitor останавливает только timer, а не текущий stream. Аналогично
копится stderr установки ключа. Большой/бесконечный ответ расходует память
main; зависший monitor остаётся busy.

**Исправление:** ограниченный reader с фактическим счётчиком байтов, budget
для entries/total bytes, дедлайны и отмена операций при закрытии сессии.
Хранить ссылку на активный monitor stream и завершать его при stop.
Не считать отображаемый лимит гарантией resource safety.

**Приёмка:** ложный metadata size, растущий файл, длинный listing, большой
stdout/stderr, команда без close. Использовать малые искусственные лимиты
в тестах; не исчерпывать настоящую память/диск.

### A11 — restoreTabs фактически включён по умолчанию

### A12 — containsSecrets=false не гарантируется содержимым экспорта

**Места:** `src/main/main.js:301–320`; `src/renderer/renderer.js:924–933`;

### A13 — сгенерированная команда SSH допускает shell injection при вставке

**Места:** `src/renderer/renderer.js:1075`; `src/main/main.js:333–337`, `:1265–1268`.

«Копировать команду ssh» конкатенирует username/host/port с пробелами без
валидации синтаксиса и shell-specific quoting. Импорт допускает metacharacters.
Например host `example.invalid; echo AUDIT_MARKER` превращается в команду
`ssh audit@example.invalid; echo AUDIT_MARKER`. Само копирование ничего
не выполняет, но вставка и Enter в POSIX shell запускают вторую команду.
Аналогичные проблемы есть с `&` в cmd и с пробелами/опциями.

**Условия:** подготовленный импортированный профиль либо ручной ввод
нестандартных значений; пользователь копирует и запускает команду.
SSH-подключение через библиотеку здесь не вызывает shell и само по себе
от данного примера не исполняет вторую команду.

**Исправление:** валидировать hostname/IP/username, отвергать управляющие
символы, строить аргументы с правильным quoting для указанного shell;
для неизвестного shell показывать явный вариант копирования. Не полагаться
на pasteGuard: опасная команда может быть одной строкой.

**Приёмка:** пробелы, `;`, `&`, `$()`, leading `-`, Unicode, IPv6,
нестандартный порт; результат не содержит дополнительных shell-команд.

### A14 — rejected SFTP promise остаётся в кэше

**Место:** `src/main/main.js:801–809`.

При первом getSftp запоминается promise. Если сервер временно отказал в

upload и повторное открытие SFTP получают ту же ошибку без нового запроса.
Успешно открытый, но затем закрытый SFTP channel также не инвалидирует кэш.

**Воспроизведение:** A14, две попытки дают только один вызов `client.sftp`.

**Исправление:** сбрасывать кэш на reject и close/end/error; защищаться от
гонки, где старый promise сбрасывает уже созданный новый.

**Приёмка:** первая попытка временно неуспешна, следующая успешна;
закрытие SFTP channel не требует пересоздания всей SSH-вкладки.

### A15 — stop tunnel закрывает listener, но не существующие соединения

**Места:** `src/main/main.js:1543–1549`, `:1565–1580`.

Обработчик stop вызывает `server.close()` и сразу удаляет запись, не отслеживая
принятые socket/SSH streams. Node прекращает новые подключения, но оставляет
старые активными — [документация net.Server.close](https://nodejs.org/api/net.html#serverclosecallback).
Интерфейс показывает выключенный туннель, хотя прежний DB/HTTP-клиент продолжает
работать через него. После удаления из map нельзя явно завершить эти socket
повторным stop.

**Воспроизведение:** A15 применяет настоящий обработчик stop к loopback
echo-listener. Уже установленное соединение возвращает `AUDIT_AFTER_STOP`
после `{ok:true}` и удаления записи. SSH forwardOut в этом тесте не участвует;
свойство сохранения TCP-соединения проверено настоящим Node net.

**Исправление:** учитывать все пары socket/channel, закрывать обе стороны
при stop, удалять их из Set на close, обрабатывать socket error сразу после
accept, включая период ожидания forwardOut. Если желаема семантика drain,
отразить это отдельным состоянием UI и предложить принудительный stop.

**Приёмка:** новые и существующие соединения после stop недоступны согласно
выбранному контракту; повторный start/stop не оставляет ресурсов.

### A16 — `./` проходит запрет удаления текущего каталога

**Места:** `src/main/utils.js:58–70`; `src/main/main.js:1431–1436`, `:1388–1401`.

`path.posix.normalize('child/../')` возвращает `'./'`, но
`isDangerousRemoteTarget` запрещает только `'.'`, `'..'`, `'/'` и `'../...'`.
Поэтому `sftpDelete(id,'./',true)` допускается и рекурсивно удаляет содержимое

не создаёт такую цель: это пробел защитного IPC-контракта, а не доказанная
атака обычным именем файла из listing. A16 проверяет только validator;
реальное удаление не выполнялось.

**Исправление:** привести trailing slash aliases к единому виду до проверки,
проверять опасные цели и при построении рекурсивного обхода. Определить
политику canonical paths и промежуточных symlink, не полагаясь только на
лексическую нормализацию.

**Приёмка:** `.`, `./`, `child/../`, `/`, `/a/../`, `..`, `../`, повторные
разделители; ни одна запрещённая цель не вызывает unlink/rmdir даже в mock.

### A17 — защита многострочной вставки покрывает не все пути

**Места:** `src/renderer/renderer.js:809–855`, `:2108–2130`;

минуя диалог pasteGuard и trim/политику MeowShell.

**Воспроизведение UI:** синтетический ClipboardEvent с двумя безопасными
строками на виртуальной вкладке. Получен `echo AUDIT_ONE\recho AUDIT_TWO`,
pasteGuard включён, диалога нет. Команды в shell не исполнялись.
Физические Shift+Insert/Ctrl+Shift+V отдельно проверить на Windows.

**Исправление:** единый paste pipeline на уровне DOM capture с проверкой
реальной терминальной цели, остановкой default propagation и вызовом
безопасной вставки без рекурсивной обработки собственного события.
Учесть native paste, Ctrl+V, Ctrl+Shift+V, Shift+Insert, context menu и
bracketed paste mode каждого получателя broadcast.

**Приёмка:** все способы вставки одинаково проходят guard; не теряется
Unicode; escape-последовательность завершения bracketed paste внутри текста
не должна превращать остаток в команды без проверки. Последний сценарий
установлен как необходимая отдельная проверка, shell E2E для него не проводился.

### A18 — вставка в настройки может попасть в скрытую сессию

**Места:** `src/renderer/renderer.js:845–847`, `:809–822`, `:1634–1641`, `:325–346`.

У settings-pane тоже есть класс `term-pane`. Глобальный capture-обработчик
Ctrl+V проверяет только `e.target.closest('.term-pane')`, отменяет нормальную
вставку в input и вызывает handlePaste. При открытии настроек прежний
`focusedSessId` остаётся ID живого терминала. handlePaste выбирает его и
вставляет текст либо загружает файл/скриншот именно в скрытую сессию.

**Воспроизведение UI:** на вкладке настроек событие Ctrl+V в `#st-fontfamily`
дало `calledTerminalPaste=true`, `prevented=true`, `activeId=__settings__`,
`focusedSessId=audit-virtual`. handlePaste был заменён счётчиком, поэтому
настоящий clipboard не читался. Дальнейший выбор ID подтверждён исходным кодом.

**Исправление:** разрешать терминальную вставку только для xterm textarea
и конкретной активной terminal cell; не перехватывать input/select/textarea
настроек, редактора, палитры и contentEditable заголовков. Определять получателя
по элементу события и сверять жизненный цикл панели, а не по старому глобальному ID.

**Приёмка:** Ctrl+V во всех полях настроек и диалогов изменяет только поле;
backend `session:write` и `paste-media` не вызываются. Тест с настоящим
clipboard проводить только с синтетическим текстом/файлом.

### A19 — smoke-тест не проверяет заявленные ключевые сценарии

**Места:** `src/renderer/renderer.js:884–886`, `:2596–2629`, `:2782`;
`src/main/main.js:1254–1255`; `.github/workflows/ci.yml`,
`.github/workflows/release.yml`; `scripts/check.js`.

`initPromise` уже проглатывает ошибку через catch и toast, после чего отдельный
`.then(smokeReady)` всё равно сообщает успех. Открытие shell, onboarding,
восстановление вкладок выполняются в другой async-цепочке и не входят в
критерий готовности. Main выходит через 500 мс. Поэтому smoke может пройти
при сломанном PTY или ошибке конфигурации. Это согласуется с обнаруженными
ошибками, которые штатные шесть tests не замечают.

В CI packaged smoke есть только для x64. Release собирает x64/arm64, но
не запускает smoke собранных артефактов ни для одной архитектуры в этом
workflow; публикация зависит от build, а не от успешного runtime-теста
публикуемых файлов. README корректно называет ARM64 экспериментальным,
но «проверка в CI» здесь в основном означает сборку и статические тесты.

**Исправление:** отдельный детерминированный smoke-сценарий с временным
профилем: дождаться полной инициализации, создать PTY, получить nonce-вывод,
проверить ввод/resize/завершение и закрыть приложение. На ошибку init — exit 1.
Запускать проверку именно публикуемого артефакта. Для ARM64 нужен соответствующий
runner или честно обозначенная ручная проверка; сборка x64-host не равна запуску ARM64.
Не отключать security checks ради прохождения smoke.

**Приёмка:** искусственное отсутствие PTY и сломанная конфигурация дают failure;
публикация недоступна при провале проверки артефакта. Шесть utils tests сохранить,
но добавить поведенческие тесты из раздела 8.

### A20 — ошибки сохранения теряются в renderer

**Места:** `src/renderer/renderer.js:901–904`, `:924–933`, `:1610–1613`,
`:2211`, `:2235`, `:2381`, `:2555`, `:2588`;
`src/main/main.js:1356–1362`.

Main возвращает `{error:...}` при неуспешном saveConfig. Многие обработчики
renderer либо вообще не ожидают promise, либо ожидают, но не проверяют error.
Например добавление snippet показывает «Команда добавлена», хотя запись могла
не состояться. Изменения остаются в памяти и исчезают после перезапуска.
Для туннелей и snapshots неуспех также не сообщается. Это отличается от
saveConnection/deleteConnection в ряде других мест, где ошибка обработана.

**Исправление:** единый awaitable save helper с проверкой результата,
ошибкой UI и политикой rollback/dirty state. Для частых изменений — очередь
или debounce с гарантированным flush перед restart. Не показывать успех
до подтверждения записи; не замалчивать rejected IPC.

**Приёмка:** mock save возвращает error/reject; UI показывает неуспех,
пользователь понимает, какие изменения не сохранены, старый конфиг цел.
Не менять права реального профиля пользователя для воспроизведения.

## 7. Дополнительные замечания и направления проверки

Эти пункты не включены в число 20 основных замечаний. Здесь меньший приоритет,
платформенные условия либо необходимость дополнительного воспроизведения.

1. **Редактор и сохранность текста.** `main.js:1449–1450` декодирует любой файл
   в UTF-8, а `:1462` пишет UTF-8; для бинарного/не-UTF-8 файла это необратимое
   преобразование. UI предлагает «Редактировать» для всех недиректорий.
   Нет dirty-confirm при Escape/outside click/закрытии (`renderer.js:1451–1477`).
   Добавить проверку кодировки/бинарности, явно обозначить преобразование,
   подтверждать потерю несохранённых правок. Проверить CRLF/LF round-trip.
2. **Host fingerprint в hex.** `hostHash:'sha256'` в ssh2 возвращает hex
   (`node_modules/ssh2/lib/client.js:283`), а широко используемый OpenSSH формат
   имеет вид `SHA256:<base64>`. Сама проверка работает, но сравнение по инструкции
   неудобно. Показывать OpenSSH-совместимый формат с явным алгоритмом;
   не сбрасывать существующий knownHosts при смене отображения.
3. **cmd.exe quoting требует Windows-теста.** `utils.js:88–94` использует `^%`
   для процентов внутри кавычек и не рассматривает delayed expansion `!`.
   Достаточная защита не подтверждена. Проверить реальные cmd `/V:ON` и `/V:OFF`
   на именах с `%VAR%`, `!VAR!`, `^`, `&`, пробелами. Не считать POSIX-тест
   доказательством корректности cmd quoting.
4. **Windows key ACL и синхронный keygen.** `main.js:1643–1662` генерирует RSA4096
   синхронно в main и может блокировать UI. `{mode:0600}` не доказывает настройку
   Windows DACL; перезапись существующего файла также не гарантирует сужение прав.
   Проверить ACL, коллизию `.pub`, частичную запись пары; генерацию вынести из main.
5. **Linux safeStorage.** Проверка `isEncryptionAvailable()` не отбрасывает
   backend `basic_text`. На Linux он может не обеспечивать ожидаемой защиты,
   что описано в [документации safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage).
   Сейчас заявлена Windows-цель, поэтому не выносится как подтверждённая Windows-
   уязвимость. Перед официальной поддержкой Linux явно отвергать basic_text
   либо честно обозначить режим без защищённого хранения.
6. **Legacy secrets.** `main.js:254–256` сначала записывает мигрируемый старый
   конфиг, затем шифрует секреты. При недоступном шифровании старое plaintext
   значение остаётся и показывается предупреждение. Старые MyTerm-файлы
   не удаляются полным reset. Уточнить политику миграции/удаления без
   самовольного удаления данных другого приложения.
7. **Рекурсивное скачивание на Windows.** Case-insensitive collisions (`a`/`A`),
   повторные entry names, зарезервированные control chars и гонки symlink/junction
   требуют отдельного набора проверок. Лексический `resolveLocalChild` не решает
   гонки файловой системы. Предпочтителен staging-каталог с эксклюзивным созданием.
8. **PTY package integrity при cross-build.** `scripts/ensure-win-pty.js:39–49`
   загружает tarball через npm pack и проверяет name/version, но не сверяет
   архив с integrity конкретной записи lockfile. npm ci защищает обычную
   установку, однако этот путь нужно проверить отдельно для foreign-arch пакета.
   Установленный пакет пропускается только по version. Не утверждается,
   что tarball реально подменён.
9. **Производительность/поддерживаемость.** Много sync FS в main; чтение config
   повторяется в mt/uiLanguage. Renderer расширяет функции цепочками `__v9*`,
   `__v10*`, `__v201*`; уже зарегистрированные event callbacks иногда держат
   старую функцию (например split-кнопка зарегистрирована до защитной обёртки).
   Есть повторные fit/resize timers, широкие catch без диагностики. Сначала
   покрыть lifecycle тестами, потом рефакторить по ответственности.
10. **i18n и пользовательский текст.** Перевод обходом DOM исключает не все
    пользовательские поля: snippet labels, некоторые titles/пути могут
    менять отображение при совпадении с фразами словаря. Это не доказанный XSS.
    Проверить «команда», «Ошибка» и похожие имена в ru/en, динамические titles,
    производительность MutationObserver на интенсивном выводе.
11. **Мелкие UX/состояния.** progressRows индексируется только filename
    (`renderer.js:960–974`), хотя события содержат session id; одинаковые имена
    параллельных загрузок смешиваются. `installKeyOnServer` из вкладки настроек
    видит activeId настроек и отказывает: использовать пункт палитры из SSH
    либо явный выбор целевого сервера. Повторное добавление public key не
    дедуплицирует authorized_keys и не учитывает отсутствующий финальный newline.
12. **Релизы.** Не сверяются git tag и package.version. Общий release-bundle
    создаётся после SHA256SUMS и не имеет собственной записи в этом manifest.
    Повторный publish скачивает `*.zip`, включая существующий bundle, что
    требует проверки идемпотентности повторного запуска. Не проверены фактические
    текущие GitHub Releases и права репозитория. Не добавлять новую публикацию
    только ради диагностики.

## 9. Как повторить доступные проверки

Из корня репозитория, Node.js 22.12+:

```bash
npm run verify
npm run audit:acceptance
npm audit --json
npm ls --depth=0
```

Диагностический скрипт читает функции из текущих исходников и использует
их без изменения. Большинство внешних операций заменены заглушками;
две проверки создают временные loopback TCP listeners (SSH banner/close
и echo) и закрывают свои sockets. Пользовательские конфиги и настоящие
SSH-сервера не затрагиваются.
Скрипт не подключён к `npm test`, потому что проверяет наличие старых дефектов.
При изменении сигнатур/маркеров исходников его надо пересмотреть.

GUI-проверку повторять только с отдельным профилем. Для root Linux-container
использованный smoke имел вид:

```bash
audit_profile=$(mktemp -d /tmp/meowshell-audit-smoke-XXXXXX)
timeout 25s xvfb-run -a node_modules/electron/dist/electron . \
  --no-sandbox --disable-gpu --meowshell-ci-smoke \
  --user-data-dir="$audit_profile"
```

На обычном пользовательском Windows-профиле `--no-sandbox` добавлять нельзя.
Приведённый smoke демонстрирует только текущую узкую проверку A19;
он не заменяет предложенный тест полного запуска и PTY.

Материалы аудита содержат технические детали потенциальных уязвимостей.
Следовать `SECURITY.md` при внешнем раскрытии; этот отчёт оставлен локально
и не отправлялся в публичные issues или третьим лицам.
